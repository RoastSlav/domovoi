## Objective

Make every approval surface show **what will run, where, with which arguments, and which plan the human is approving**, rendered by deterministic code (never model prose), and make the approve request carry the **current v1 plan hash** that the card showed. The action writer refuses an approval whose hash does not match the action's stored v1 hash, changing nothing.

Surfaces in this prompt:

- the web `ActionCard` and approve dialog (used on the Approvals page and the incident page);
- the Discord card (embed text and button labels);
- the platform-neutral markdown card (`render.rs`, used by notifiers and fallbacks).

**Must not be built here:** plan hash v2, script-byte or target-identity binding, `execution_id`, approval-binding columns on actions, `POST /operations/{id}/steps/{step}/approve`, any operation or step concept. Those belong to later milestones (prompts 22 and 27). F4 must not claim script-byte or target-identity binding in any text, comment, test or doc.

## Architectural context

Plain-terms background (RW-11 "Stages", RW-22; decision D-02 keeps approvals human-only):

- **Why structured cards.** Today the Discord Approve/Deny buttons name no skill, host or arguments, and the card text is model prose. A prompt-injected model therefore writes what the human reads when approving. After this change the approval block is built from the stored `ActionRequest` (skill, host, arguments, risk, plan hash, expiry); model text, where shown, is labelled as the model's and is secondary.
- **What the v1 plan hash covers** (existing, do not change): SHA-256 over `plan:v1\n{skill}\n{manifest_hash}\n{host_id}\n{canonical args}`. It binds the **skill name, the manifest hash, the host id and the canonical arguments**. It does **not** bind the entry-script bytes (only the manifest) and does **not** bind a resolved target identity (host only). It is stored on the action when proposed (immutable) and **recomputed at dispatch** from the agent's current manifest; a difference rejects the action (INV-4).
- **What the new approve-time check adds.** The approve request carries the hash the card displayed. The writer compares it with the action's stored v1 hash and refuses a mismatch before the status changes. This makes the approval an approval *of the plan the human saw* (a stale or substituted card cannot approve a different plan), and keeps the binding explicit in the request. It is **not** a new runtime boundary against a compromised hub: the hub can compute the hash itself. Runtime limits remain dispatch recomputation, the agent's local checks and the audit log. Say this honestly in docs and comments; do not call it script or target binding.
- **Web vs chat.** The web request carries the **full 64-hex** hash. A Discord button's `custom_id` is limited to 100 characters and an approval is already 95, so it can carry only a **3-byte (6 hex) prefix** of the hash (4 base64url characters: the ID is then exactly 100 characters). The single-use chat token remains the authenticator for chat; the prefix is a staleness check. The writer accepts either form through `PlanBinding`.
- **Destructive actions** are still web-only with typed confirmation (INV-6); chat shows them with a link, unchanged.
- **Arguments must never be hidden from the approver.** A card that cannot show all arguments within a fixed budget does not offer chat Approve/Deny for that action; it offers the web link instead (fail safe).
- **No approval path is added.** `HumanApproval::new` stays in `crates/domovoi-hub/src/auth/` only; the LLM tool catalogue is untouched; nothing but an authenticated human approves.

## Required interfaces and contracts

### Core (**fixed**)

```rust
// approval.rs
impl PlanHash {
    /// The first 8 hex digits, for cards and logs. Not a security value.
    #[must_use] pub fn short(&self) -> String;          // hex::encode(&self.as_bytes()[..4])
}

/// The plan hash an approval request says it is approving.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum PlanBinding {
    /// The whole hash (web).
    Full(PlanHash),
    /// The first 3 or more bytes of the hash (a chat button, whose custom ID has no room for more).
    Prefix(Vec<u8>),
}
impl PlanBinding {
    /// Shortest prefix accepted, in bytes.
    pub const MIN_PREFIX: usize = 3;
    /// Whether this binding names `stored`. A prefix shorter than MIN_PREFIX or longer than 32 never matches.
    #[must_use] pub fn matches(&self, stored: &PlanHash) -> bool;
}
```

`Full` compares all 32 bytes; `Prefix(p)` requires `MIN_PREFIX <= p.len() <= 32` and `stored.as_bytes().starts_with(p)`. Comparisons need not be constant time (the hash is not secret), but use the straightforward `==`/`starts_with`.

## Protocol and compatibility

- **Agent protocol:** unchanged (1.1). Nothing in `domovoi-proto` or `domovoi-agent` changes.
- **HTTP API:** `POST /api/v1/actions/{id}/approve` now requires `plan_hash` (400 without it). `ActionDto` gains `plan_hash`. This is a deliberate API tightening; the only first-party client is the embedded web UI, updated in the same change. State it in the PR description.
- **Cards already posted:** Discord buttons from before the upgrade lack the prefix and are refused with a clear message; proposals expire after 1 hour (`PROPOSAL_TTL`), and the dispatcher refreshes open cards after a restart, so the window is short. Do not add a bypass.
- **Stored cards/JSON:** `Card.plans` is `#[serde(default)]`, `plan_prefix` is optional, so older serialized cards still parse.

## Error handling and recovery

| Situation | Exact behaviour |
|---|---|
| Web approve with a hash that equals the stored one | Approved as today. |
| Web approve with a different 64-hex hash | Writer returns `PlanChanged`; action stays `Proposed`; HTTP 409 `conflict` with the specific message; web dialog shows "Could not approve the action" and the message inline. |
| Web approve without `plan_hash`, or not 64 hex | HTTP 400 `bad_request`; nothing changes. |
| Approve for an unknown action id | HTTP 404 (lookup first), as today. |
| Chat press with matching 3-byte prefix and valid token | Approved as today. |
| Chat press with a prefix that does not match | `PlanChanged`: reply "This card is out of date; open the incident to review it"; token is **not** consumed (the writer returns before clearing the token); action stays `Proposed`. |
| Chat press of an old button (no prefix) | Hub replies "This card is out of date; open the incident in the web UI to approve"; the service is not called. |

| Prefix shorter than 3 bytes (crafted) | `PlanBinding::matches` is false: `PlanChanged`. |

## Security requirements

- **Check order in the writer:** load -> chat token (chat only) -> plan binding -> state transition. The binding check never has side effects.
