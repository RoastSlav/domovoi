# 0032. Helper safety attestation

- Status: Accepted
- Date: 2026-11-22

## Context

Unattended containment on a host needs the owner's management paths to be confirmed and current, and a path may be confirmed only when a verified helper attestation shows it covered. The hub must not take the agent's word for what the helper enforces: a compromised agent could declare any path covered. The proof is a signed report of what the helper enforces, verified by the hub against a key the owner pinned. The helper's identity is in [0030](0030-three-identities.md), its delivery in [0031](0031-helper-and-skill-runner-delivery.md) and the hub's half in [0035](0035-helper-attestation-boundary.md). The pure contract is the `attest` module of `domovoi-core`; its frozen vectors live in `crates/domovoi-core/tests/attest/vectors/`.

## Decision

1. **What is signed, by whom.** The helper computes the report and signs it with its Ed25519 key. The agent relays the bytes unchanged. The signing input is `domovoi-safety-attest-v1`, LF, then the full report bytes, for complete and incomplete reports alike. The two hashes inside the report use their own prefixes (`domovoi-safety-config-v1`, `domovoi-safety-routes-v1`). With no usable key the helper returns an unsigned closed token; the hub treats it as `attestation_missing`.
2. **Verification order.** The hub checks the signature over the received bytes first, with `verify_strict` against the pinned key, then parses those same bytes with a strict parser that never re-serialises, then recomputes both hashes from the report's own lines. The steps are: decode (public key, report at most 64 KiB, 64-byte signature), pin lookup, key comparison, signature, strict parse, hash recomputation or minimal-shape check, nonce, then the generation rules.
3. **Acceptance and trust.** The hub accepts a report as verified state only if the signature verifies with the pinned key, the nonce is valid and `complete=true`. Trust follows the latest outcome per host: a key mismatch, a validly signed incomplete report or a generation regression revokes the verified state, and one later good attestation restores it. There is no sticky mismatch flag. The gate on every use (permit issuance, dispatch, confirmation) requires: the key pinned; the latest outcome not a mismatch; a stored verified state; `now - nonce_issued_at < 300 s`; every confirmation current (fingerprint, generation and both hashes equal, less than 30 days old; `boot_id` may differ for confirmations only); every candidate path covered.
4. **Key lifecycle.** `domovoi helper init` creates the directory (0700), the key (exclusive create 0600, `fsync` of file and directory), the lock and a state file at generation 0 with zero hashes, only when neither key nor state exists. The helper never generates a key implicitly. `rotate-key` makes a new key and a new state, deletes the old private key once the new files are durable and moves the old public key, fingerprint and state to `retired/<timestamp>/`. `recover` handles lost or damaged state the same way and always creates a new key, because continuity cannot be proven after state loss. Start checks refuse a wrong mode and never repair it ([0031](0031-helper-and-skill-runner-delivery.md)).
5. **Pinning.** The hub computes the fingerprint (lowercase hex SHA-256 of the 32 raw key bytes) itself and ignores any value an agent sends. Nothing is pinned on first contact. The owner compares the hub's fingerprint with the one `domovoi helper fingerprint` prints on the host, confirms with the account password and the full fingerprint typed from the host, and the hub pins the exact 32 bytes. A different key from the pinned one is a mismatch; the old pin is kept.
6. **Nonce and freshness.** 32 random bytes per request, for one host, single use, valid for 60 seconds, with the issue time stored. Boundaries are strict. Freshness is measured from the nonce issue time, not from hub receipt. The nonce is consumed only after the signature, parse and hashes pass, so a forged reply cannot burn it.
7. **Generation and the high-water mark.** The generation is a u64 per key that counts changes of the effective safety set; it increases by exactly one when the freshly computed hashes differ from the persisted ones, and is unchanged by a containment membership change or a new `boot_id` with identical content. A change followed by its revert advances it by two. The hub stores, in the transaction that accepts the report, the highest accepted `(generation, config_hash, route_state_hash)` per helper and key, and rejects a lower generation, or an equal generation with different hashes, as `generation_regressed`. A complete report with generation 0 is rejected.
8. **Fail-closed state.** Key and state valid and matching is the only normal condition. State missing with a key present, state corrupt, the state's key fingerprint not matching the key, key missing with state present, both missing and an interrupted write each refuse all containment and are never reset automatically; recovery is a local root action. A wrong mode or an unopenable lock is `helper_state_permissions`, distinct from `state_corrupt`. The state write is ordered before signing (temp file, `fsync`, `rename`, directory `fsync`, all inside the lock), so no signed `complete=true` report names a generation that is not durable.
9. **Encoding.** The report is a set of LF-terminated `key=value` lines in a fixed order, accepted only when it is already canonical (every line parses strictly and re-renders to identical text).
   - `incomplete_reason` is the only key whose value may be empty, and it is empty if and only if `complete=true`.
   - A `complete=false` report has one minimal shape: generation 0, both hashes 64 zeros, a non-empty reason token, `max_ttl_s=0`, `max_active=0` and no repeated lines. The hub requires exactly that shape and uses nothing from it but the token and the receipt time.
   - Interface names in `iif` and `oif` selector items are encoded with the strict field encoder before the items are joined by `;`, and the joined selector is encoded once, so a name containing `;` or `=` cannot be confused with a selector boundary.
   - Grammars: interface names (15 bytes decoded), ports 1 to 65535, table, priority and metric as canonical `u32`, `max_ttl` as digits plus one of `s m h d` with 0 refused, unit names with a known type suffix (a backslash is allowed), unknown `[safety]` keys refused, ranges with `start <= end`.
   - The vectors `C1` to `C4` and `R1` to `R4` and the signed samples are frozen and never regenerated; new vectors are added beside them.
10. **`expected_safety`.** A containment request carries `expected_safety` as a closed tagged value: `verified` with the full identity, or `unverified` with one reason. It is a consistency guard for the honest path, not proof of a hub permit. The helper requires it on every `Contain` request and refuses a missing or malformed one (`malformed_safety`). With `verified` the helper recomputes and compares the identity (`safety_changed`, or `safety_unknown` when it cannot compute it). With `unverified` only the comparison is skipped: overlap, maxima, mutation limits and fail-closed behaviour still apply. The type refuses extra fields, unknown tags and unknown reasons. The wire reason is the closed set `key_not_pinned`, `key_mismatch`, `attestation_missing`, `attestation_stale`, `signature_invalid`, `report_incomplete`, `generation_regressed`, `path_uncovered`, `confirmation_stale`; richer detail stays in audit and logs. The `ExpectedSafety` and `HelperIdentity` types are part of protocol 1.2.
11. **Apply-time limits.** A requested TTL above the effective maximum (the smaller of the helper's `max_ttl_s` and the agent's limit) is refused (`ttl_above_maximum`), never clamped. `max_active = 0` means no containment is allowed, so the default configuration refuses everything. The active count comes from the helper's own view of the nft set. The mutation limit is persisted under the helper's state directory with a boot-aware age rule, so a restart never reopens the window.
12. **Route-state observation.** A policy rule whose action is not lookup, a selected route whose type is not unicast and a non-UTF-8 interface name are reported as `complete=false` with `route_unrepresentable`: the helper refuses containment rather than hash a state that omits something. Hosts whose routing the observation cannot represent get no containment.
13. **Races.** A change of configuration, relevant network state, `boot_id` or generation between attestation, permit and apply is refused as `safety_changed`; a comment-only edit is not. The lock protects helper state, not the kernel: a route change between recomputation and apply is the accepted race, and the next attestation sees it.

## Consequences

- A forged key blocks containment only until the next honest attestation, not until a rotation.
- A rolled-back or restored helper state is detected by the high-water mark; it needs write access to the helper directory, which also holds the key.
- The unverified human path needs the account password, a typed confirmation and a "not protected" display, and is audited `containment.unverified_approved`. No policy permit is ever issued with `unverified`. A compromised agent can call the helper with `unverified`; it still cannot forge an attestation, widen the helper's set or exceed its maxima.
- The report vectors prove encoding, sorting and hashing, not the selection logic. Live route observation (policy routing, tunnels, several tables, `iif`, `fwmark` and `uidrange` semantics) needs validation on real Linux hosts, and the key's custody through the real helper binary depends on the file permissions of [0030](0030-three-identities.md).
- Rules `ATTEST-1` to `ATTEST-10` are in [0035](0035-helper-attestation-boundary.md).

## Alternatives considered

- A hub-signed permit the helper verifies: needs a helper-side trust root, hub signing-key custody and rotation, and a protocol change.
- Trusting the agent's description of the helper: a compromised agent could declare any path covered.
- Generating the helper key implicitly on first start: a missing key must fail closed so an attacker cannot force a fresh, unpinned identity.
- Computing real hashes at `init` (generation 1): `init` would need a valid configuration and a working observer at install and recovery.
- Keeping retired private keys: no use, and a live credential against any remaining pin.
- A different selector separator, or refusing names that contain `;` or `=`: the inner escaping removes the ambiguity and the kernel accepts such names.
- Clamping an over-long TTL, or treating `max_active = 0` as unlimited: clamping hides an over-long request and the unlimited default is unsafe.
- Widening the wire reason enum to carry every detail: detail stays internal.
