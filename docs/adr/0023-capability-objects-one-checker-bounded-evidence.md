# 0023. Capability objects, one checker, bounded evidence

- Status: Accepted
- Date: 2026-11-17

## Context

After 0022 three things remained. Every engine subsystem still held one object that could do anything: `ActionDeps` and `Evidence` carried `Arc<dyn AgentLink>`, so whether a scheduler could start a skill was a scanner's judgement, not a type. At the time the enforcement ran as a line-based scan with four separate rule lists in `xtask`, and the gate tests kept their own copy of the text-counting mechanism - two implementations of one rule, and a bypass that survived both was formatting-dependent (a call split across lines, a renamed import, a macro) and filename-dependent (a test-only file was exempt by its name, so a production module living under a test-like path went unscanned). And one ask inside the read boundary could hold a caller forever: `collect_evidence` awaited availability before the read with no bound, and the read's own error path in the hub's link, which looks the session up in the store when no session is connected, had no deadline either, while the hub's profile collector calls it under a 20 s deadline.

## Decision

- Capability objects. `crates/domovoi-core/src/ports/caps.rs` defines one narrow trait per operation family an engine subsystem needs - `AvailabilityProbe`, `HostObservation`, `HostRead`, `HandoffRunner`, `JournalStatus`, `CheckRerun` - and two bundles: `ActionCaps` (probe, observer, journal, handoff, rerun) and `EvidenceCaps` (probe, observer, read). `ActionDeps` carries those five objects instead of a link, `Evidence::new` takes an `EvidenceCaps` and the `Clock`, and `HostCatalog` takes one `HostObservation`. The hub turns its one `PolicyLink` into capabilities exactly once, in `crates/domovoi-hub/src/runtime/caps.rs`, and hands out the bundles; the composition root stays the only place the raw link and its policy wrapper meet. The testkit wraps its fake the same way, so a test harness receives the same shapes it hands the engine. A capability object cannot perform an operation it cannot name: the type decides before any scanner runs, and no engine module - today, or added tomorrow under `actions/` or `evidence/` - can reach the raw link through `ActionDeps`.
- One checker. `xtask` is a library plus its binary, and `domovoi-engine` and `domovoi-hub` take it in their `[dev-dependencies]` only; R5 reads "testkit and xtask are dev-only". `xtask::arch::ast::exec_violations(&[(path, text)])` is the one implementation of the boundary rules: `cargo xtask arch-check` and both crates' gate tests call it, over the real tree and over fixture trees, and report `file:line`. Each file is parsed with `syn`, falling back to parsing it as one function body, and a file that parses neither is refused. The checker visits the syntax tree and the token streams of macros. The boundary operations are cards: an exact count per exact site file, default-deny elsewhere. `WriteCommand::Dispatch` has two cards counted on different nodes, a `syn::ExprStruct` in `execute.rs` and a `syn::PatStruct` in `writer.rs`, and a third default-deny card for every other mention of the path; each occurrence is counted once. Naming (`AgentLink`, `WsAgentLink`, `PolicyLink`) and the accessors are a per-file allowlist of exact files. The accessors are recognised as method calls and fields (`.link()`, `.link_field`) and as associated paths, `AgentServer::link` and `AgentServer::link_for_tests`, called, taken as function items or written as `<AgentServer>::link` or `Self::link` inside an `impl AgentServer`; `use` renames of the type or of the accessor and `type X = AgentServer;` are resolved first, and the type is part of the match so an unrelated `link` function is not flagged. `AgentServer::link` is also private to the `agent_server` module, so the compiler stops code outside it before the checker is consulted; the runtime composes through `AgentServer::policy_link`.
- Source classification and coverage. Which files only tests compile is decided by module wiring, never by file name. `xtask::arch::reach::explore` follows `mod name;`, `#[path = "..."]` and `include!("...")` from every Cargo target root in two contexts, production and test, resolving paths as `rustc` does and visiting each file at most once per context. Test roots are the Cargo `test` targets; libraries, binaries, build scripts, examples and benches are production roots, so none of them is exempt. A declaration under `#[cfg(test)]` (inherited through nested modules; `all(test, ..)` counts, `any(test, unix)` and `not(test)` do not) moves its target to the test context. A file is test-only exactly when the test context reaches it and the production context does not, so a file also loaded by a production module is scanned as production. A file nothing reaches is production. Rust loaded from outside `crates/` by a production `#[path]` or `include!` is read, scanned and checked against every crate's EXEC rules. The checker refuses, as `SRC-1` with the declaring file and line, a module or `include!` whose file is missing, whose path leaves the workspace or enters `target/` or `.git/`, whose `#[path]` is not a string literal or is set by `cfg_attr`, and an `include!` whose argument is not one string literal. `include_str!` and `include_bytes!` are data and are not followed. The line rules (R2, R3, R4, INV-1) read the text through a small lexer, `xtask::arch::lex`, which blanks comments (line, doc, nested block) and, for code rules, the contents of string, raw string, byte string and character literals while keeping line numbers; the rules that look for a string (R4's shell literals, the `plan:v2` line) read the literals.
- Bounded asks. `collect_evidence` keeps the whole ask inside the request's deadline. A `Clock::now()` already past it answers `Timeout` before anything is asked; otherwise the availability check races the deadline on the `Clock` port, and the result is re-checked once before the read. The read itself is bounded by the `HostRead` contract (`caps.rs`): every await inside `read_host`, error classification and fallback included, ends by the deadline with `LinkError::Timeout`, and a request it registered is released however the call ends. `Evidence` does not wrap the read in a second race, because dropping the read future at an arbitrary point is what the contract avoids. The hub's `WsAgentLink` meets the contract: the network wait races the deadline; the `NotConnected` fallback, which reads the store to tell a missing agent from an incompatible one, races the same deadline, and nothing is registered while it runs; and a registered request is released by a guard that runs on drop, so a caller that abandons the future leaves no pending request. `start_skill` uses the same fallback and the same bound. `AgentLink::availability` is not bounded by the link; `Evidence` races it, as before. Ordering (availability, then enablement, then the read), argument validation and error classification are unchanged. The bounding tests advance a fake clock while a check or a lookup is pending and assert entry through a notifier; nothing sleeps.

## Consequences

- A subsystem's reach is its fields: `ActionDeps` has no read object, so actions and triage cannot read a host through it, and `EvidenceCaps` has no handoff, so the read boundary cannot start a skill. Widening a subsystem is an explicit edit in the hub's `runtime/caps.rs`, which a reviewer sees.
- There is no pair of scanners left to disagree: arch-check and both crates' gate tests call the same `exec_violations`, so a card or walker bug fails both sides at once, and the gate fixtures that push bypasses onto a fixture tree keep the implementation honest from inside the crates.
- The checker has limits, and they are stated here rather than hidden. Glob re-exports of the type or accessor are not resolved. A type alias is resolved only when it is a plain path to the type (`type Server = AgentServer;`), not through a generic wrapper or a trait projection. An attribute macro's arguments are not walked and a `#[cfg(test)]` function (as opposed to a module) is not pruned, so such code is scanned as production. `#[path]` inside an inline module is approximated. The checker sees source text, so code generated at build time into `OUT_DIR` is not seen: an `include!` of it is refused as `SRC-1` instead. The `xtask/` directory is the tool itself and is not scanned. The engine and hub gate tests call `cfg_test_closure`, which has no Cargo metadata and treats the files nothing else loads as production roots; the CLI is the only caller that follows files outside the crate. The cards' exact counts and the gate fixtures turn these limits into checked behaviour for the code that exists today.
- A profile collected against a hung availability check, or against a host whose session vanished while the store was slow, now answers four "timed out" sections instead of blocking the profile scheduler indefinitely; the minute scheduler retries later.
- The new dev-only edges `domovoi-engine` -> `xtask` and `domovoi-hub` -> `xtask` are covered by R5; R1 only governs normal edges, so the dependency table is unchanged and nothing in a product build links `xtask`.
- The checker moved from the tool's binary into its library, and the library now has to answer both the tool and the gate tests, so the library file carries the same `#![allow(clippy::print_stdout, clippy::print_stderr, clippy::disallowed_methods)]` the tool's binary already had: xtask is a developer tool, it runs `cargo metadata` and `git` directly and prints its report. The package keeps `[lints] workspace = true`, so R7 holds, and every product crate keeps the workspace set and the process and console rules that R3 and the Clock rule guard there.
- Every limit above is a statement about what the checker sees, not about runtime behaviour: nothing here changes an operation's semantics.
- No wire, storage or API shape changes; the capability objects carry no new operation, they re-partition the one 0022 fixed.

## Alternatives considered

- Capability objects were rejected in 0022's alternatives for the link newtype; revisited here because the objection no longer holds: `JournalStatus` covers the reconciliation and journal queries the engine needed beside a run, and the traits name only the operation a subsystem may ask for, while the scanner keeps guarding naming and raw call sites.
- Keeping the line scans and patching their known bypasses: two implementations of one rule would drift again at the next formatting trick, and exempting test-only files by name is wrong in principle - production code wearing a test-like name is production. Rejected.
- Sealing the capability bundles so the compiler forbids any other construction: `async_trait` objects are open at their construction sites, so a seal the hub cannot route around is not expressible without an escape hatch; a default-deny naming rule plus the capability fields gets the same result for reviewable code. Rejected, and stated above as a limit.
- Checking the deadline only after the availability await returned: a hung check would still pin the profile scheduler's slot forever. Rejected.
- Wrapping the whole `read_host` future in an outer `select!` in `Evidence`: it would drop the future at an arbitrary await and skip the link's cleanup. The adapter bounds its own awaits and releases its request on drop instead. Rejected.
- Treating every file whose name looks like a test as test-only, or every file a `#[cfg(test)]` module loads as test-only: a production module can load the same file, and production code must never escape the scan because a test also uses it. Rejected in favour of two reachability contexts.
