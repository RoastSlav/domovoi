# 0022. One execution boundary and one read boundary

- Status: Accepted
- Date: 2026-11-17

## Context

The hub runs a skill from exactly one place today: an approved action reaches the executor's run task, which re-checks the incident, waits for the host, re-validates the skill, recomputes the plan hash, commits `Approved → Dispatched` through the one writer, and only then hands the request to the agent. Host reads are almost as concentrated: the model's tools and the profile collector both call `AgentLink::run_tool`, and the triage context calls it in a third place.

Two things were still missing. Nothing in the code or CI said *where* those calls may live, so a new transport, a scheduler or an admin endpoint could add a second path to `start_skill` or `run_tool` and no check would notice. And the raw link was reachable from any module in the hub through `AgentServer::link()`, so a transport could hold one and skip the use case entirely.

`04 §8.1` and `03 RW-08` asked for a single execution boundary and a single read boundary with a gate; the mechanism the repository already uses for rules like this is a line-based source scan in `xtask arch-check`, backed by a gate test.

## Decision

- `execute(AuthorizedExecution)` in `crates/domovoi-engine/src/actions/execute.rs` is the only function that dispatches and the only caller of `AgentLink::start_skill`. `AuthorizedExecution` has one crate-private constructor, `of`, called at exactly one site (the executor's per-action run task, immediately before `execute`); it carries the action and its `ExecutionId`, is taken by value, and is never serialised, stored or logged in full. `execute` refuses an action with no stored human approval, refuses a policy authorization, and refuses an expired window without writing an outcome of its own; expiry inside the run task stays the writer's `NotRun`.
- `execute` keeps two separately named hashes: the approval-family hash the `Dispatch` command carries (v2 for new actions, recomputed from the host's current enrolled key) and the always-v1 `runskill_plan_hash` on the wire, which the agent recomputes.
- `collect_evidence(EvidenceRequest)` in `crates/domovoi-engine/src/evidence/` is the only caller of `AgentLink::run_tool`. Its `EvidenceScope` is built from the incident or host the caller was given, so a caller cannot pass a host beside an incident. It checks the host's availability first and answers `NotConnected` or `Incompatible` before any request is built, so an unavailable host never shows a skill's error in place of the connection's; only for a `Known` host does it apply the enablement that exists at M1 (the closed `ReadToolCall` set, the read-only skill rule, and the arguments the skill's manifest accepts), and it returns the agent's `ToolOutput` unchanged. Redaction, truncation and the cut notes stay with the callers that own them. It is not the only way to learn about a host: host metadata is read through `AgentAdmin`, and verification re-runs a check with `run_check`.
- `HostCatalog` is the narrow, non-tool view of an agent (session snapshot, announced skills, presence) that triage and profile collection need beside their reads. It replaces `Arc<dyn AgentLink>` in `TriageDeps` and `ProfileDeps`.
- `AgentServer::link()` is crate-private. The composition root builds `Evidence`, `HostCatalog` and `PolicyLink` from it once; the API reads presence, skills and logs through `AgentAdmin`, which delegates to inherent methods on `AgentServer`. The raw link reaches a test suite only through `link_for_tests`, which is compiled only with the hub's `test-support` feature. That feature is not a default: only the hub's and the binary's own `[dev-dependencies]` turn it on, so their test targets can drive an agent's wire while a normal or release build has no method that hands the link out; the public `WsAgentLink` re-export exists in the same two configurations only. Asking for the feature by name (`--features test-support`, or `--all-features`) compiles the accessor too, exactly as any other Cargo feature would - Cargo cannot make a feature unenableable, only keep it out of the builds nobody asks for; no CI job or `cargo xtask ci` path asks, and a deployed hub is built without it.
- Four rules, each a constant allowlist and a line-based scan: `EXEC-1` (`run_tool(` only in the evidence boundary), `EXEC-2` (`run_skill(`, `start_skill(` and `run_capability(` only in `execute.rs`), `EXEC-3` (`run_check(` only in verification), `EXEC-4` (a transport may not name `AgentLink`, `WsAgentLink` or `PolicyLink`, nor take the link from the server with `.link()` or `.link_for_tests()`). `EXEC-1` to `EXEC-3` scan the sources of `domovoi-core`, `domovoi-engine`, `domovoi-hub` and `domovoi-store`; `EXEC-4` scans `domovoi-core`, `domovoi-engine`, `domovoi-hub` and the binary. Each is default-deny, so a transport directory added later is covered without an edit. The trait declaration file `agent_link.rs` is the only `ports/` exception for `EXEC-1` to `EXEC-3`; for `EXEC-4` the core `ports/` exceptions are that file plus `ports/mod.rs`, which re-exports the trait, and any other port module added beside them is denied. The real link, the policy wrapper and testkit keep their own entries. The agent, runner and protocol crates have their own request handlers and are out of scope of EXEC-4.
- Gate tests assert the same shape from inside the engine and the hub. `single_execution_boundary` counts non-comment occurrences, several on one line included, and requires exactly one `AuthorizedExecution::of(`, one `execute::execute(`, one `start_skill(`, one `run_tool(` and one `run_check(`, plus exactly one `WriteCommand::Dispatch {` construction in `execute.rs` beside exactly one match in the writer. Each permitted file carries its own expected count instead of an exemption, so the writer's legitimate match is counted rather than the file being excused: a second one there fails as a second construction anywhere else does, and a second call in any permitted file fails, not only a call in a forbidden one. `transports_do_not_name_the_agent_link` is default-deny over the hub's `src/` except `agent_server/` and `runtime/`, and refuses the accessor even when the returned type is never written down.

## Consequences

- There is one path from a human decision to a running skill, and one from a caller to a host's tool output; adding a second one now fails CI instead of passing review.
- `AgentLink` gains no method and the wire does not change: this is a consolidation, not a capability.
- `run_check` stays outside the read boundary: verification re-runs a declared check after a run, it is not evidence and not read-only. A later operation layer may move it with the verification effect.
- The enforcement is textual. A renamed re-export, a macro, a fully qualified call such as `AgentServer::link(&server)`, or a call split across lines is not caught, and nothing here is a compiler seal; the counts are non-comment text matches, not resolved calls. The value is that the ordinary way to add a second path, or for a transport to take the link, fails `arch-check` or a gate test.
- A new `AgentLink` implementation must be added to `LINK_DEFINITION_PREFIXES`, which is a deliberate edit a reviewer sees.
- `test-support` is a test configuration, not a capability: it adds one accessor to the hub's test builds and no behaviour to a shipped binary.
- No table, column, endpoint, message or DTO changes; `AuthorizedExecution` never leaves memory and the evidence boundary stores nothing.

## Alternatives considered

- A trait or newtype around the link handed to the engine, with `start_skill`/`run_tool` only on the newtype: the compiler would enforce it, but the engine already receives the link through one port and the hub would still need a route to the raw link for reconciliation and journal queries. The scan was chosen because it also catches a transport that names the type without calling it.
- Keeping `AgentServer::link()` public and relying on review: a transport could hold a link and add a second path with no failing check. Rejected.
- A `#[doc(hidden)]` accessor available in every build: it hides a method from the rendered docs but leaves it callable by any consumer, so the boundary would rest on convention. The non-default `test-support` feature was chosen instead, because the accessor then is not in a normal artifact at all.
- Moving verification's `run_check` into `collect_evidence`: it would make a non-read-only call look like evidence, and the verification effect (a later milestone) is where it belongs. Rejected.
- A database column recording the execution id: `ExecutionId` is derived from the action at M1 and nothing needs to be stored. Rejected.
