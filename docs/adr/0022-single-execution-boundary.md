# 0022. One execution boundary and one read boundary

- Status: Accepted
- Date: 2026-11-17
- Implementation hardened by [0023](0023-capability-objects-one-checker-bounded-evidence.md): capability objects, one syntax-aware checker and bounded evidence. Where this record and 0023 describe the same mechanism, 0023 is current.

## Context

The hub runs a skill from exactly one place today: an approved action reaches the executor's run task, which re-checks the incident, waits for the host, re-validates the skill, recomputes the plan hash, commits `Approved → Dispatched` through the one writer, and only then hands the request to the agent. Host reads are almost as concentrated: the model's tools and the profile collector both call `AgentLink::run_tool`, and the triage context calls it in a third place.

Two things were still missing. Nothing in the code or CI said *where* those calls may live, so a new transport, a scheduler or an admin endpoint could add a second path to `start_skill` or `run_tool` and no check would notice. And the raw link was reachable from any module in the hub through `AgentServer::link()`, so a transport could hold one and skip the use case entirely.

`04 §8.1` and `03 RW-08` asked for a single execution boundary and a single read boundary with a gate; the mechanism the repository already used for rules like this was a line-based source scan in `xtask arch-check`, backed by a gate test. That was the first implementation; [0023](0023-capability-objects-one-checker-bounded-evidence.md) replaced it with one syntax-aware checker.

## Decision

- `execute(AuthorizedExecution)` in `crates/domovoi-engine/src/actions/execute.rs` is the only function that dispatches and the only caller of `AgentLink::start_skill`. `AuthorizedExecution` has one crate-private constructor, `of`, called at exactly one site (the executor's per-action run task, immediately before `execute`); it carries the action and its `ExecutionId`, is taken by value, and is never serialised, stored or logged in full. `execute` refuses an action with no stored human approval, refuses a policy authorization, and refuses an expired window without writing an outcome of its own; expiry inside the run task stays the writer's `NotRun`.
- `execute` keeps two separately named hashes: the approval-family hash the `Dispatch` command carries (v2 for new actions, recomputed from the host's current enrolled key) and the always-v1 `runskill_plan_hash` on the wire, which the agent recomputes.
- `collect_evidence(EvidenceRequest)` in `crates/domovoi-engine/src/evidence/` is the only caller of `AgentLink::run_tool`. Its `EvidenceScope` is built from the incident or host the caller was given, so a caller cannot pass a host beside an incident. It checks the host's availability first and answers `NotConnected` or `Incompatible` before any request is built, so an unavailable host never shows a skill's error in place of the connection's; only for a `Known` host does it apply the enablement that exists at M1 (the closed `ReadToolCall` set, the read-only skill rule, and the arguments the skill's manifest accepts), and it returns the agent's `ToolOutput` unchanged. Redaction, truncation and the cut notes stay with the callers that own them. It is not the only way to learn about a host: host metadata is read through `AgentAdmin`, and verification re-runs a check with `run_check`.
- `HostCatalog` is the narrow, non-tool view of an agent (session snapshot, announced skills, presence) that triage and profile collection need beside their reads. It replaces `Arc<dyn AgentLink>` in `TriageDeps` and `ProfileDeps`.
- `AgentServer::link()` is private to the `agent_server` module: nothing outside it can call it. The composition root obtains the link only wrapped in the skill policy, through `AgentServer::policy_link`, and builds `Evidence`, `HostCatalog` and the action capabilities from that `PolicyLink` once; the API reads presence, skills and logs through `AgentAdmin`, which delegates to inherent methods on `AgentServer`. The raw link reaches a test suite only through `link_for_tests`, which is compiled only with the hub's `test-support` feature. That feature is not a default: the hub's and the binary's `[dev-dependencies]` turn it on, so their test and development builds can drive an agent's wire, while a normal or release build has no method that hands the link out. Asking for the feature by name (`--features test-support`, or `--all-features`) compiles the accessor too, exactly as any other Cargo feature would - Cargo cannot make a feature unenableable, only keep it out of the builds nobody asks for. CI test builds do compile it, because the dev-dependencies activate it; a deployed hub is built without it.
- Four rules, each default-deny and checked by one syntax-aware checker ([0023](0023-capability-objects-one-checker-bounded-evidence.md)): `EXEC-1` (`run_tool` only in the evidence boundary), `EXEC-2` (`run_skill`, `start_skill`, `skill_result` and `run_capability` only in their cards' files), `EXEC-3` (`run_check` only in verification), `EXEC-4` (a transport may not name `AgentLink`, `WsAgentLink` or `PolicyLink`, nor take the link from the server with `.link()`, `.link_for_tests()`, `AgentServer::link`, `AgentServer::link_for_tests` or the same paths through a renamed import or a type alias). `EXEC-1` to `EXEC-3` scan the sources of `domovoi-core`, `domovoi-engine`, `domovoi-hub` and `domovoi-store`; `EXEC-4` scans `domovoi-core`, `domovoi-engine`, `domovoi-hub` and the binary. Each is default-deny, so a transport directory added later is covered without an edit. The trait declaration file `agent_link.rs` is the only `ports/` exception for `EXEC-1` to `EXEC-3`; for `EXEC-4` the core `ports/` exceptions are that file plus `ports/mod.rs`, which re-exports the trait, and any other port module added beside them is denied. In the EXEC rules every exception names one file exactly, so a new file added beside an allowed one inherits no exception, and a path that merely starts with a file entry is refused too. The agent, runner and protocol crates have their own request handlers and are out of scope of EXEC-4.
- Gate tests assert the same shape from inside the engine and the hub by calling the very checker `cargo xtask arch-check` runs ([0023](0023-capability-objects-one-checker-bounded-evidence.md)), over their crate's production sources and over fixture trees they build. `single_execution_boundary` refuses any boundary violation in the engine; `the_boundary_gate_counts_each_operation_exactly_once` builds the smallest tree that satisfies the engine's cards and pushes each bypass onto it, and `dispatch_construction_and_match_are_separate_sites` checks that `WriteCommand::Dispatch { .. }` is one struct expression in `execute.rs` and one struct pattern in `writer.rs`. `transports_do_not_name_the_agent_link`, `the_link_scan_sees_an_untyped_accessor` and `a_new_transport_file_cannot_take_the_link_by_path` run the same rules over the hub's whole `src/`, with the naming exceptions named file by file.

## Consequences

- There is one path from a human decision to a running skill, and one from a caller to a host's tool output; adding a second one now fails CI instead of passing review.
- `AgentLink` gains no method and the wire does not change: this is a consolidation, not a capability.
- `run_check` stays outside the read boundary: verification re-runs a declared check after a run, it is not evidence and not read-only. A later operation layer may move it with the verification effect.
- The enforcement is syntax-aware, not a compiler seal: the checker parses the sources, so a call or an accessor split across lines, a renamed import, a type alias or an operation hidden inside a macro does not slip through, code inside comments and string literals never counts, and a file that does not parse is refused rather than skipped. Its limits are listed in 0023. The value is that the ordinary way to add a second path, or for a transport to take the link, fails `arch-check` or a gate test.
- A new `AgentLink` implementation names the trait, so it must sit in a file the `EXEC-4` naming allowlist lists, which is a deliberate edit a reviewer sees.
- `test-support` is a test configuration, not a capability: it adds one accessor to builds that enable it - the hub's and the binary's test and development builds, or any build that asks for it by name - and no behaviour to a shipped binary.
- No table, column, endpoint, message or DTO changes; `AuthorizedExecution` never leaves memory and the evidence boundary stores nothing.

## Alternatives considered

- A trait or newtype around the link handed to the engine, with `start_skill`/`run_tool` only on the newtype: the compiler would enforce it, but the engine already receives the link through one port and the hub would still need a route to the raw link for reconciliation and journal queries. The scan was chosen because it also catches a transport that names the type without calling it.
- Keeping `AgentServer::link()` public and relying on review: a transport could hold a link and add a second path with no failing check. Rejected.
- A `#[doc(hidden)]` accessor available in every build: it hides a method from the rendered docs but leaves it callable by any consumer, so the boundary would rest on convention. The non-default `test-support` feature was chosen instead, because the accessor then is not in a normal artifact at all.
- Moving verification's `run_check` into `collect_evidence`: it would make a non-read-only call look like evidence, and the verification effect (a later milestone) is where it belongs. Rejected.
- A database column recording the execution id: `ExecutionId` is derived from the action at M1 and nothing needs to be stored. Rejected.
